# Tumblr Integration System

Tumblr運営・Telegram集客連携のモジュールRepository。TGtumbler親Projectの一部であり、新しい親Projectを設けません。既存MPB / GATE / 告知・応募の責務を重複開発せず、API・イベント経由で接続します。

**Status:** Source開発中。Tumblr実OAuth、Telegram実連携、Gserver配備、操作アプリの実ブラウザ受入は未検証。

## Scope
- 9 modules: account, discovery, library, media, engagement, publishing, campaigns, referrals, analytics.
- Mobile chat: 6 visible objectives + free text; AI proposes purpose-grounded actions and NEXT; 79-action catalog is a tool index, not a rigid wizard.
- Gemini for writing/planning, Groq for simple commands, OpenRouter free-only fallback; no paid automatic fallback.
- One recruitment Tumblr account only; private account excluded.

## Operation center (priority: Master 2026-11-10)

Source: `app/index.html`, `app/styles.css`, `app/app.js`, `tumblrkit/assistant.py`. The home screen is a conversation. Sending does not require a module button. The nine modules stay an internal toolbox, and the bridge's allowed actions are the tool index. The canonical six-goal shortcuts are now rendered as optional multi-select buttons: 巡回／投稿／キャンペーン／紹介／集計／メディア. The nine modules remain internal. Selecting a goal adds its scope to the Assistant request; it does not execute an external action. Recovery controls (retry, draft, abort, confirm) appear only after a proposal or a failure. Provider calls use injected `TUMBLR_GEMINI_API_KEY`, `TUMBLR_GROQ_API_KEY`, and free-only `TUMBLR_OPENROUTER_API_KEY`. With no key, the reply says the provider is absent and does not claim the action ran. Publish and announcement actions stay on preview until confirmation. No client-side credential storage.

Local UI inspection: build a stamped release, inject `TUMBLR_APP_ACCESS_TOKEN` (16+ characters, not stored in Git), then run `python -m tumblrkit.appserve serve`. The process binds loopback only. `/` requires that token; `/healthz` and `/version` return the release commit and do not return the screen. `python -m tumblrkit.appserve rollback` switches `dist/current` back to the previous release. This command does not change DNS, Tunnel, Access, or Secrets. Master approved the candidate `tumblr.hentaigay.org`; a public lookup found no record, and the record is not created until the existing Tunnel and Access target are read back. **Do not publish the UI unauthenticated**. The six shortcuts use the previously adopted labels and remain optional; free-text submission does not require a button selection. Nine module names remain internal and do not gate the chat.

Tests: `PYTHONPATH=. python -m unittest discover -s tests -v`, `node --check app/app.js`. A passing static test does not establish browser/user acceptance.

OAuth Source: `tumblrkit/oauth.py` is an isolated adapter requiring injected transport and deployment Secret. Secure state lifecycle/refresh and live account readback are incomplete. Master reports the required Secret is already obtained; do not ask for reissue or write it to Git.

Development rules: [G-ACE GPT CHAT Rule Plane](https://github.com/G-ACE-inc/server-core/issues/17). Work only on owned branches; no secrets or personal data in this public repository.

## Free AI quota guard (offline-source implementation)

GitHub Actions Secrets (`TUMBLR_GROQ_API_KEY`, `TUMBLR_GEMINI_API_KEY`, `TUMBLR_OPENROUTER_API_KEY`) are **not** automatically available to the Gserver process. Never echo, copy or inject them from CI without the existing Gserver private-Secret owner path and separate runtime authorization.

Live provider calls are **OFF by default**, even if keys are present. Before any real request, operations must explicitly set **both** `TUMBLR_AI_LIVE_ENABLED=1` and `TUMBLR_AI_QUOTA_DB` to an existing writable persistent SQLite-file location owned by the app (not in Git, not in a temporary/ephemeral release directory). Do not enable these during CI or quota tests. Every real request is reserved before HTTP and counted even on failure; a missing/unwritable database blocks calls.

Conservative fixed source-side limits: **5 attempts per provider per UTC day, 10 attempts total across three providers per UTC day, and minimum 60 seconds between requests across all providers**. Counters survive process restart and are shared by processes using the same SQLite file. Provider HTTP 429 / exhausted quota does not trigger fallback. Fallback to OpenRouter remains only when a primary provider fails for another reason and the quota guard permits it. OpenRouter remains free-model-only. These are additional local safety caps, **not proof of provider-side free-tier terms or current model availability**.

All `tests/test_free_ai_quota.py` checks are local mocks/SQLite and never call the three AI service APIs. Successful tests do not authorize Gserver live activation. No client-side API keys, paid escalation, or automatic load testing.

## Owner login and local drafts (Source implemented, 2026-11-10)

The application now serves an unauthenticated **login form** at `/login` and returns a 401 login page for unauthenticated `/`. The already configured private `TUMBLR_APP_ACCESS_TOKEN` is used for sign-in. Successful browser sign-in creates a random **HttpOnly, Secure, SameSite=Strict** server-side session, expires after 12 hours; the owner token itself is never placed in a browser cookie or script. Authenticated browser writes require same-origin checks. An external/public Cloudflare Access policy is **not** enabled; the existing app-owned authentication remains the protection, not a verified identity/SSO integration.

The operation screen has **実物の下書き管理**: input text → `入力を保存` → `保存一覧を表示` → `編集する` / `削除`. Endpoints `GET/POST /drafts`, `DELETE /drafts/<id>` require the owner session or bearer credential. Drafts live in the app's own persistent SQLite at `<resolved-release-root>/data/drafts.sqlite3`; no AI, Tumblr or Telegram calls occur during draft operations. The app must have filesystem permissions on this location and the release root must persist across revisions. All draft input is length-checked and secret-like patterns are redacted, but **do not enter credentials or sensitive personal data in drafts**. Existing release rollback swaps static assets and does not delete drafts.

Important: GitHub PR #1 Source/CI changes require an explicit **existing Gserver owner app lifecycle release** to update the live `tumblr.hentaigay.org` process. Passing CI, `/healthz` for an older revision, or a GitHub commit is not runtime acceptance. Do not claim the new login/draft controls are live until the public HTTPS owner login, CRUD and revision readback are observed. All AI providers remain disabled by default and the free-token live calls have **not been tested**.

## Existing Gserver app live update (owner key required once)

A live process without a persistent owner token file cannot be safely restarted by copying secrets from process memory. A source commit is not a live deployment. The original `TUMBLR_APP_ACCESS_TOKEN` stored only in the old process is not extracted or logged. The **owner** performs a one-time WSL password choice with `scripts/tumblr_owner_setup.py`; the helper prompts twice using hidden input, creates a mode-0600 private file `~/.config/tgtumbler/tumblr-operation-app/tumblr-app-access-token` (private parent directory), then invokes `scripts/tumblr_release.py`. This is an owner-authorized replacement of the inaccessible old application login key; it must not be performed automatically in CI or by GPT CHAT. It does not change the three AI provider API keys.

`tumblr_release.py` requires a clean existing `feat/initial-modular-core` checkout and a fresh exact Source SHA, builds a separate `dist-staging` release, tests a temporary loopback service on 8082 for version, unauthenticated login, authenticated UI and draft list **without any inference calls**, then updates the existing versioned `dist` release and replaces only the one existing Tumblr operation app on 8081, with a rollback attempt if new live readback fails. It never manages unrelated Bots, DNS/Tunnel or Gserver core. Do not mark accepted until the HTTPS login and authenticated draft readback are independently observed.

The operation app starts with `TUMBLR_AI_LIVE_ENABLED=0` even if GitHub Actions Secrets exist. It remains a **partial product**, since external Tumblr OAuth and the three AI keys' safe Gserver injection still require separate completion. No CI test or bootstrap claims those APIs have run.

## Chat attachments (owner-only, local files)

The compact Assistant composer has a plus (`＋`) control for selecting up to five attachments per message, each up to 8 MiB. Supported formats: JPEG, PNG, GIF, WebP, PDF, UTF-8 plain text, DOCX, XLSX, PPTX, ZIP. The server validates file signatures/types and bounds, stores the uploaded bytes and private metadata under the app-owned version-independent `dist/data` directory, and serves images only after owner authentication. Other documents are delivered as downloads, not HTML. Private `DELETE /attachments/<id>` supports cleanup; the release acceptance smoke checks upload, authorized retrieval, Assistant reference and cleanup without making external API calls.

**Product boundary:** Attachment upload means the private Assistant chat received a file. It does **not** publish to Tumblr/Telegram or imply AI vision, PDF analysis, or provider connectivity. Until a multimodal adapter and approval flow are implemented, the Assistant explicitly acknowledges receipt without claiming to have interpreted file contents. Uploads must not be mistaken for a Tumblr media post.

## Verified-result view contract (2026-11-11, Source work)

The Assistant uses the existing bridge's provider-verified response (not generated or guessed content) to return a bounded `view` for successful actions. Each action has stable column names and order; the browser renders them as a compact, scrollable table with HTTPS-only source links. Numeric nonnegative analytics rows can additionally render a data-derived bar chart. All content is inserted as text nodes, never AI-supplied HTML. The view limits display to 100 records and retains total/truncation metadata. An absent adapter still reports `not_connected` and provides no fabricated view.

Current limitation: the six bridge actions do not imply that Tumblr OAuth, Telegram, media retrieval or analytics adapters are connected. The view consumes `rows` or `items` only from a verified adapter response. Provider connection, live account readback, full nine-module mapping, media previews and public HTTPS browser acceptance remain separate work. No image or video generation is introduced.

## Official Tumblr read-only posts adapter (source implementation)

A conditional `tumblr.list_posts` adapter now uses the official fixed HTTPS Tumblr API endpoints and checks `/v2/user/info` for the configured blog before returning up to 20 posts. `summary/title`, `type`, `date`, and verified source `post_url` are mapped to the established fixed-column result view. The action stays read-only; no post creation, deletion, or changed access policy is introduced.

Required **app-owner runtime configuration**: `TUMBLR_OWNER_BLOG` (the single owned recruitment-blog identifier) and `TUMBLR_OAUTH_ACCESS_TOKEN_FILE` (path to a private, owner-managed OAuth access token file, mode 0600). This is **not** `TUMBLR_APP_ACCESS_TOKEN` and must never be substituted with the browser login key or copied into GitHub. Both settings absent means the prior unconnected behavior. No OAuth flow, refresh lifecycle, production Secret injection, or actual live Tumblr read has been verified by this Source change. An unavailable/invalid token or mismatched owner returns failure, not fabricated records. Other Tumblr/Telegram/analytics adapters remain separate, currently unconnected work.

Tumblr NPF image/video blocks now supply an optional `thumbnail_url` in the fixed list view; only HTTPS thumbnails hosted on Tumblr media domains are eligible for inline image rendering. Original posts remain accessible via validated source links. Missing media previews show an empty cell rather than generated content. Existing chat and six-button layout are unchanged.

## Account module: production OAuth onboarding (2026-11-11)

Account is the **first of nine existing internal modules**, not a new top-level Project or a seventh goal shortcut. The previously registered Consumer Key and Consumer Secret stay in the private owner directory `~/.config/tgtumbler/tumblr-oauth/` as `consumer-key` and `client-secret` (0600). They are never copied to Git, client JavaScript, logs or the app login token.

The existing owner-authenticated Assistant header has a small `Tumblr連携` action. On first use, no blog name is requested: the owner authorizes the initial Tumblr account first. Then the official `/v2/user/info` response is checked for exactly one `primary: true` blog, which is bound to the OAuth token. The app does not create a Tumblr blog. An existing explicit `TUMBLR_OWNER_BLOG` or private `owner-blog` retains the prior strict selection behavior for already configured deployments. No unrelated blog is selected without verified account ownership. `POST /oauth/configure` and `POST /oauth/start` require existing owner authentication and browser same-origin, and start returns only Tumblr's official OAuth authorization URL. The Tumblr application's registered OAuth2 redirect must exactly match `https://tumblr.hentaigay.org/oauth/callback`. **Do not automatically alter the Tumblr application, DNS, Tunnel or Access settings to make it match.**

The `/oauth/callback` handler accepts an authorized callback only with a short-lived, single-use server-held state generated on `/oauth/start`, exchanges code for OAuth2 access/refresh tokens, and checks that `/v2/user/info` includes the selected recruitment blog. Only then it atomically writes private `account-tokens.json` and `access-token` (0600). Refresh uses `offline_access` and the same private client credentials; unknown/expired/revoked authorization fails closed. The existing `tumblr.list_posts` read adapter can consume the managed bearer without a duplicate API implementation. No Tumblr post publication, account deletion or unrelated Bot changes are part of Account.

**Important verification distinction**: tests with a fake Tumblr transport are only Source/CI evidence. Live acceptance requires the Tumblr application callback registration, owner authorization in a browser, a verified blog readback, successful real API list readback, correct production SHA and successful HTTPS browser verification. A bare successful release or UI button display does not constitute a connected Tumblr account.

## Tumblr provider safety: Account → read-only discovery boundary

Tumblr publishes default API limits of 1,000 calls/hour and 5,000 calls/day per consumer key. These are **upper limits, not safe operating targets or protection against account suspension**. Tumblr's API terms and community rules also prohibit spam, misleading mass activity and attempts to evade platform restrictions.

The existing official `TumblrReadAdapter` has a persistent, private, per-Owner SQLite safety budget at `~/.config/tgtumbler/tumblr-oauth/tumblr-api-budget.sqlite3`. The two Tumblr requests used by one explicit `tumblr.list_posts` action are reserved together **before any network request**. Current conservative local limits: at most **12 read-related API calls/hour, 30/day**, and a minimum **60 seconds between read actions** (across restarts/processes sharing the file). A 429 response freezes read operations for at least 24 hours, with **no automatic retry** and no fallback to scraping, another key, browser automation or a different account. Disk, permission, quota or identity errors **fail closed**, not fail open. These local thresholds are safeguards, not a promise of provider permissions or availability. Do not perform live API load/stress testing to test the limiter; use offline mocks and persisted SQLite tests.

This limiter applies to the **read-only post-list adapter**, not a blanket guarantee for all nine modules. Account OAuth consent and token refresh use separate official endpoints; they must not be stress-tested either. Future Discovery / Publishing / Engagement modules must implement appropriate persistent quotas, idempotency and consent **before** any new live API calls. Never auto-follow/auto-like/auto-reblog, perform bulk posting, create blogs in a loop, rotate credentials or circumvent rate limits. Use explicit, purpose-appropriate source checks, short bounded results, caching and manual confirmation for protected effects.

Release safety: the existing `scripts/tumblr_release.py` staging/live smoke uses only loopback app endpoints and private file fixtures, not Tumblr production endpoints. An offline CI PASS is not a live provider acceptance. Do not repeatedly invoke real Tumblr identity/posts merely to reconfirm already verified credentials.

## Discovery module — adopted full contract, not merely tag search

**Owner:** the existing internal `discovery` module inside `tumblrkit`; one authorized Tumblr recruitment account only. The original adopted scope (2026-10-29, preserved in `01_gap_review.md`) includes (1) explicitly selected following blogs, (2) followers of the one owner blog, (3) publicly visible candidate posts through relevant tags, (4) source attribution, checkpoints, deduplication, exclusion and unavailable-status tracking, (5) durable handoff to Library/Viewer, Publisher and Analytics. The existing six-goal Assistant UI stays the only home; no new menu or separate runtime.

**Official read-only endpoints:** `GET /v2/user/following`, `GET /v2/blog/{owner}.tumblr.com/followers`, `GET /v2/tagged`, and explicitly requested one-post checks `GET /v2/blog/{blog}.tumblr.com/posts?id=...`. No arbitrary host or scraping is allowed. Entry via `tumblr.discover` accepts `対象: following`, `対象: followers`, `対象: tag:タグ`, `対象: related:タグ`, or an unprefixed tag for compatibility. One page of up to 10 results per action, never an uncontrolled loop. Owner may click **続きを取得** to advance the persisted cursor, or **新しく確認** with explicit warning to refresh from page one. A completed source opens the privately stored candidates without further network calls.

**Durability:** `tumblrkit/discovery_store.py` stores `discovery_sources` (cursor/watermark/complete), `discovery_blogs`, `discovery_posts` and many-to-many provenance link tables in an owner-private SQLite file under the already adopted `~/.config/tgtumbler/tumblr-oauth` folder. Candidate IDs are stable; repeated occurrences do not create duplicate candidates, and cross-source membership is preserved. Provider failures do not advance a source checkpoint. A verified exact-ID 404 can mark one candidate `unavailable`, but an incomplete page or network outage is never interpreted as a deletion. Image/video metadata and links may be stored, **not downloaded media bytes**. The separately owned Library/Viewer and Media Save modules consume these stable records; they retain their own pending acceptance, including favorites/history, permissions and conversion.

**Owner-only local controls:** `GET /discovery/candidates` returns the existing private cache; `POST /discovery/exclude` excludes a chosen blog locally after owner authentication and origin checks. The compact result row's **除外** action requires an explicit click and confirmation and makes no Tumblr block/unfollow request. Existing metadata links are https-only and candidates from unverified external URL origins are rejected rather than auto-fetched. The `tumblr.discover` result keeps fixed table columns and supplies only validated hidden blog/candidate references. Browser cache/localStorage does not store secrets.

**Ban/API-risk boundary:** All discovery source requests reserve **one** call in the shared persistent provider safety budget *before* token/API work, with conservative read limits (12/hour, 30/day, 60 seconds between read actions; a 429 pauses at least 24 hours). No retries, background scanning, auto-follow, reblog, like, message, bulk publishing, or credential rotation. This is stricter than Tumblr published API quotas but is **not a guarantee against account restriction**. Tests use only stubbed official responses and temporary local SQLite files; the existing release smoke uses local loopback APIs and does not deliberately request live Tumblr discovery.

**Acceptance state:** Source, offline mocks, and Gserver runtime are verified independently; a CI pass or read-only app deployment alone is **not** proof of live followers/tag API permission, all edge cases of Tumblr's ever-changing results, external browser workflow, or end-to-end downstream Library/Publisher/Analytics. These remain separate, explicit validation steps to be checked without repeated live account tests. Do not promote the module to fully accepted until the adopted Discovery handoff and user workflow are verified.
